## Архитектура видеосистемы

Видеоконтроллер Sprinter реализован в FPGA **ACEX 1K30** (файл `VIDEO2.TDF`) и имеет следующие ключевые характеристики:

| Параметр | Значение |
|---------|---------|
| VRAM | 2 × 256 КБ (512 КБ всего) |
| Организация VRAM | 4 независимых банка по 8 бит (32-битный доступ/такт) |
| Частота кадров | ~50 Гц (PAL) или 60 Гц (NTSC) |
| Режимы | ZX (256×192), 320×256 8bpp, 640×256 4bpp |
| Палитра | 256 цветов из 16 777 216 (24-битный RGB, 8-8-8) |
| Double buffering | Поддерживается через RGMOD |

### Физическая структура VRAM

```
VRAM 512 КБ
├── Банк 0 (8 бит) — 128 КБ
├── Банк 1 (8 бит) — 128 КБ
├── Банк 2 (8 бит) — 128 КБ
└── Банк 3 (8 бит) — 128 КБ
```

Все 4 банка работают параллельно — за один такт видеоконтроллер читает 32 бита (4 пикселя в режиме 320×256 8bpp).

## Страницы VRAM

VRAM доступна через банкинг как страницы `#50`–`#5F`. Младшие биты номера страницы — это **флаги режима записи**, а не отдельные области памяти:

```
Номер страницы VRAM: #5X, где X = %TSPP

  бит 3 (T) — прозрачность: 1 = байт #FF пропускается при записи
  бит 2 (S) — только VRAM: 1 = запись идёт только в видео-ОЗУ (DRAM не трогается)
  бит 1..0 (PP) — смещение внутри видеобуфера (0–3 = 16 КБ × 4 = 64 КБ)
```

Одна и та же физическая VRAM доступна через **разные номера страниц** с разным поведением записи. Например, `#50` и `#58` указывают на одни и те же пиксели, но `#58` дополнительно включает прозрачность `#FF`.

### Режимы записи в VRAM

| Бит T | Бит S | Страницы | Режим записи |
|-------|-------|---------|-------------|
| 0 | 0 | `#50`–`#53` | **Обычная**: пишет в VRAM и в DRAM одновременно |
| 0 | 1 | `#54`–`#57` | **Только VRAM**: DRAM не затрагивается |
| 1 | 0 | `#58`–`#5B` | **Прозрачность**: `#FF` пропускается; DRAM обновляется |
| 1 | 1 | `#5C`–`#5F` | **Прозрачность + только VRAM**: идеально для спрайтов |

Из `SP2_ACEX.TDF`:
```
BLK_MR = (VIDEO_PG & (DECODE.PAGE[2] or (DECODE.PAGE[3] & ACC.GLISSER)));
```
`BLK_MR` блокирует запись в основную DRAM: всегда при `PAGE[2]=1`, или при `PAGE[3]=1` и байт = `#FF`.

### Зачем бит S (только VRAM)?

Видео-ОЗУ Sprinter — **теневое ОЗУ**: оно физически отделено от DRAM, но при обычной записи (`S=0`) данные автоматически дублируются в DRAM. Это позволяет CPU прочитать то, что отображается на экране. При `S=1` дублирование отключается — запись идёт **только** в видео-ОЗУ, DRAM сохраняет прежнее содержимое.

Главное применение — **спрайты**: при `S=1` программа рисует спрайт только в видео-ОЗУ, а в DRAM остаётся **чистый фон** (без спрайта). Когда спрайт нужно стереть или переместить, достаточно скопировать фон из DRAM обратно в видео-ОЗУ — не нужно хранить отдельный буфер «что было под спрайтом».

Из `ARHITECT.TXT`: *«Запись видео-данных может производиться и без перезаписи данных в основном ОЗУ, что оказывается полезным при работе, например, со спрайтами.»*

### Прозрачность `#FF` (бит T)

При `T=1` **любая** запись (CPU `LDIR`, `LD (HL),A` или акселератор) проверяется аппаратно:
- Байт ≠ `#FF` → записывается как обычно
- Байт = `#FF` → **запись пропускается**, на экране остаётся предыдущий фон

Это позволяет рисовать прямоугольные спрайты с «прозрачными» пикселями одной командой `LDIR`.

### Константы

```asm
VPAGE_TILES     EQU #50     ; экран, обычная запись (фон, заливка)
VPAGE_SPRITES   EQU #5C     ; экран, прозрачность + только VRAM (спрайты)
```

### Переключение экранов (double buffering)

Бит 0 порта `RGMOD` (`#C9`) выбирает, какой экран отображает видеоконтроллер. Программа рисует в неактивный экран, затем переключает. Подробнее — в разделе [5.7 Double buffering](07_double_buffer.md).

Примеры кода работы с режимами VRAM, прозрачностью и double buffering — в разделе [5.9 Примеры графики](09_examples.md).

## Организация видеопамяти: 1 КБ на строку

VRAM-страница `#50` физически организована как массив **256 строк × 1024 байта**. CPU «видит» одну такую строку через любое окно (`WIN0..WIN3`), куда подключена страница `#50`. Какую именно строку — задаёт регистр `PORT_Y` (порт `#89`).

### Карта 1024 байт одной строки

```
смещение в строке  байты      содержимое
┌─────────────────┬───────┬───────────────────────────────────────┐
│ $000..$13F      │   0..319 │ Пиксели экрана A (320 байт)          │
│ $140..$27F      │ 320..639 │ Пиксели экрана B (320 байт)          │
│ $280..$2FF      │ 640..767 │ Резерв                                │
│ $300..$39F      │ 768..927 │ Дескрипторы тайлов/знакомест:         │
│                 │          │ 40 × 4 байта (только в config-строках)│
│ $3A0..$3DF      │ 928..991 │ Резерв (стандартом не используется)   │
│ $3E0..$3FF      │ 992..1023│ Палитра: 8 страниц × (R, G, B, Y) — см. [5.5](05_palette.md) │
└─────────────────┴───────┴───────────────────────────────────────┘
```

Источник раскладки: ACEX K50 (`acex/K50/VIDEO2.TDF`, регистры `MODE0/MODE1/MODE2`, `MODE3` закомментирован и не подключён) + MAME (`mame/src/mame/sinclair/sprinter.cpp`, функции `vram_w`, `as_mode`, `draw_tile`).

* **Пиксели экранов A/B** — в режиме 320×256 8bpp один байт = один пиксель = индекс палитры. Экран A и экран B живут в одной и той же 1024-байтной строке, их можно показывать поочерёдно (double buffering) переключением `RGMOD`/`PG3`.
* **Дескрипторы тайлов/знакомест (`$300..$39F`)** — 40 четырёхбайтных записей (по числу горизонтальных макроячеек 640/16). Описывают, чем рисовать каждую ячейку: тайл, символ, атрибут палитровой группы. ACEX читает только 3 байта на запись (MODE0/1/2 из банков VDM3/VDM2/VDM1); 4-й байт записи аппаратно не используется. Эти дескрипторы лежат не в каждой строке, а только в «config-строках» VRAM-страницы — индексы строк задаются `RGMOD` (`row = 1 + 2*col + 0x80*(rgmod&1)` для горизонтальной макроячейки `col`). Программируемые точки растровых прерываний задаются в этой же области в подходящих строках (см. логику `is_int_updated` в MAME).
* **`$3A0..$3DF` — резерв.** Стандартная ACEX-конфигурация эту зону не декодирует. Используется только в специальных game-конфигурациях (например, *Thunder in the Deep* — там через `m_conf` включается `screen_update_game`, который читает 4-й байт дескриптора как scroll-регистр). В обычных программах **в эту область не пиши** — байты будут проигнорированы железом, но могут лечь в путь акселератора при пакетных операциях.
* **Палитра (`$3E0..$3FF`)** — см. [5.5 Палитра](05_palette.md).

### `PORT_Y` как «скользящее окно»

`PORT_Y` (порт `#89`, OUT-only) выбирает индекс строки 0..255. CPU видит **только эту одну** 1024-байтную строку, отображённую в адресном пространстве через любое окно с VRAM `#50`:

```
адрес обращения CPU
   ┌─ старшие биты [15:14] — выбор окна (WIN0..WIN3): не доходят до FPGA
   │   ┌─ биты [13:10] — игнорируются для VRAM #50
   │   │   ┌─ младшие 10 бит [9:0] — смещение внутри строки
   ▼   ▼   ▼
0bWW WWxx OOOO OOOO
        └─────┴── используется
PORT_Y → выбирает, какая из 256 строк сейчас под этим окном

физический байт VRAM = m_vram[ PORT_Y * 1024 + (CPU_addr & 0x3FF) ]
```

Из этого следствия:

1. **Линейная адресация `BASE + y*320 + x` не работает «сама собой»**. CPU не видит подряд 81920 байт экрана — он видит одну строку 1024 байта. Чтобы попасть в пиксель `(x, y)`:

   ```asm
       ld   a, y               ; индекс строки
       out  (#89), a           ; PORT_Y = y
       ld   hl, base + x       ; внутри строки: смещение 0..319 для экрана A
       ld   (hl), color
   ```

2. **Все 256 строк адресуются одним и тем же CPU-адресом**, меняется только `PORT_Y`. Это и есть «скользящее окно»: один и тот же физический адрес `$C000..$C3FF` (если VRAM `#50` в WIN3) при разных значениях `PORT_Y` смотрит на разные 1024-байтные блоки.

3. **CPU-окно не влияет на содержимое строки** — только младшие 10 бит адреса декодируются. `WIN1+$43E0`, `WIN3+$C3E0`, `WIN0+$03E0` — все три обращения попадают в палитровый регистр `R` текущей строки `PORT_Y`.

4. **Палитра живёт в той же VRAM-странице, что и пиксели**. Чтобы записать палитру `[i]`, ставим `PORT_Y = i` и пишем в `($+3E0..$+3E2)` — это записывает байты палитры для цвета `i`, не задевая пиксели (так как пиксели в `$000..$27F`, а палитра в `$3E0..$3FF`).

5. **Видимая «битая» область экрана**. Если `PORT_Y` указывает на строку 0..255, а CPU пишет в эту строку любые данные (включая, например, переменную), картинка в этой строке «прыгает». Поэтому после любой работы с VRAM `PORT_Y` загоняют в зону `$C0..$FF` (см. правило №1 ниже): аппарат рисует только первые 192/256 строк, выше — буфер не отображается.

## Видеорежимы

### ZX Spectrum (256×192, 8-цветные атрибуты)

Полностью совместим с ZX Spectrum 48K/128K:
- 6912 байт экрана (256×192 пикселей / 8 = 6144 + 768 атрибутов)
- Адресация: нелинейная (стандартная ZX)
- Маппинг: WIN1 (`0x4000`) при `SC0=1`

### 320×256, 8bpp (256 цветов)

**1 байт = 1 пиксель**. CPU обращается к буферу **не линейно**, а через окно `#50` +
`PORT_Y` (см. [«PORT_Y как скользящее окно»](#port_y-как-скользящее-окно)):
- строку выбирает `PORT_Y` (`#89`), пиксель `(x, PORT_Y)` буфера 0 — по `#C000 + x`,
  буфера 1 — по `#C140 + x` (`x` 16-битное, 0..319);
- объём одного экрана: 320 × 256 = **81 920 байт**; оба буфера интерливятся в одной
  1024-байтной строке (буфер 0 — байты 0..319, буфер 1 — 320..639).

### 640×256, 4bpp (16 цветов из 16М)

Линейный буфер, **2 пикселя = 1 байт** (старший ниббл = левый пиксель). 16 одновременных цветов выбираются из полной 24-битной палитры (16 777 216 комбинаций RGB):
- Адрес: `BASE + (y*640 + x) / 2`
- Объём: 640 × 256 / 2 = **81 920 байт** (~5 страниц по 16 КБ)
- Double buffering возможен (2 экрана помещаются в 512 КБ VRAM)

### Текстовый режим 80×32

Видеоконтроллер имеет **аппаратный текстовый режим** 80×32 (и 40×32) символа, шрифт 8×8, 640×256. Атрибут — CGA: `FLASH[7] | PAPER[6:4] | INK[3:0]` (мерцание глифа есть). Несколько знакогенераторов; ячейка выбирает слот через `MODE0`. Подробности и примеры — [5.8 Текстовый режим](08_text_mode.md).

## Ключевые порты видеоконтроллера

| Порт | Имя | Назначение |
|------|-----|-----------|
| `#82`/`#A2`/`#C2`/`#E2` | WIN0–WIN3 | регистры страниц окон памяти |
| `#89` | `PORT_Y` / `RGADR` | строка растра / индекс палитры (**только запись**; `IN` возвращает CBL) |
| `#C3` | `ALL_MODE` | режим видео (ZX / 320 / 640) |
| `#C9` | `RGMOD` | double-buffer flip (бит 0), screen on/off |
| `#FE` | ZX compat | бордюр в ZX-режиме (биты [2:0]) |

> ⚠️ **Публичные vs внутренние порты.** Прикладные программы должны использовать только
> порты выше и вызовы DSS/BIOS (`RST #10`). Сырые регистры DCP/видеоконтроллера ACEX
> (внутренние линии `DIR_PORT[]`, регистры `SC/CNF/PN/HOLD/FN_ACC/ALT_ACC` и т.п.)
> управляются прошивкой и **меняют смысл/значение после инициализации** — на них нельзя
> полагаться. В частности, `RGMOD0`/`RGMOD1` в исходниках FPGA — это внутренние линии
> `DIR_PORT[3]/[4]`, **а не** биты 3/4 порта `#C9`; приложению доступен только **бит 0**
> публичного `#C9`.

## Установка видеорежима

Рекомендуемый способ — через DSS `SetVMod` (функция `#50`): `A` = код режима, `B` = номер
экрана (0/1), `C` = `#50`, затем `RST #10`. Коды режимов (источник — `Estex-DSS/DSS/API/
SetVMod.asm`):

| `A` | Режим |
|-----|-------|
| `#02` | текст 40×32×16 |
| `#03` | текст 80×32×16 |
| `#81` | графика **320×256×256** |
| `#82` | графика 640×256×16 |

Включение одного экрана (320×256, экран 0):

```asm
Dss.SetVMod     EQU #50

        ld      a, #81          ; 320×256×256c (не путать с числом «1»!)
        ld      b, #00          ; экран 0
        ld      c, Dss.SetVMod
        rst     #10
```

`GetVMod` (`#51`) возвращает `A` = текущий режим, `B` = отображаемый экран.

> Для **двойной буферизации** режим нужно установить на **обоих** экранах (0 и 1) — пример
> и пояснение в [5.7 Двойная буферизация](07_double_buffer.md#инициализация-режим-на-обоих-экранах).

> ⚠️ Прямой порт `ALL_MODE` (`#C3`) принимает компактные коды (`#00`/`#01`/`#02`), но
> штатный и переносимый путь — DSS `SetVMod`: он настраивает дескрипторы **обоих** экранов
> и видеоконтроллер целиком. Прямую запись в `#C3` используйте только осознанно.

### Дескриптор экрана: что именно делает SetVMod

`SetVMod` не пишет видеопорты напрямую. Он выбирает готовый **8-байтный дескриптор окна** и
передаёт его в BIOS `WIN_OPEN`, который и программирует видеоконтроллер (per-cell
дескрипторы в config-строках, см. ниже). Формат записи (`Estex-DSS/DSS/API/SetVMod.asm`):

| Смещение | Поле | Назначение |
|----------|------|-----------|
| +0 | `HORIZONTAL` | ширина окна в знакоместах |
| +1 | `VERTICAL` | высота окна в знакоместах |
| +2 / +3 | `X-COORD` / `Y-COORD` | позиция окна (в знакоместах) |
| +4 | `MODE` | режим знакоместа (текст/графика, палитра, геометрия) |
| +5 | `EXT MODE` | бит0=1 → «special screen» (ZX-адресация) |
| +6 / +7 | `VRAM X/Y OFFSET` | смещение в VRAM (в знакоместах) |

Готовые дескрипторы (значения `MODE` и `X OFFSET` — ключевые):

```
;            H  V  X  Y  MODE         OFFX OFFY
текст 80x32: 40,32,0,0, %0001'1011,0,  0,  0
текст 40x32: 40,32,0,0, %0011'1011,0,  0,  0
640x256 #0:  40,32,0,0, %0000'0000,0,  0,  0
320x256 #0:  40,32,0,0, %0010'0000,0,  0,  0
640x256 #1:  40,32,0,0, %0100'0000,0, 40,  0
320x256 #1:  40,32,0,0, %0110'0000,0, 40,  0
```

**Откуда берётся `#C140`.** Два экрана двойного буфера отличаются полем `MODE` и
**`VRAM X OFFSET`**: экран 0 → offset `0`, экран 1 → offset `40` знакомест = **320
пикселей**. Поэтому в CPU-view (см. [«PORT_Y как скользящее окно»](#port_y-как-скользящее-окно))
буфер 1 начинается на `+320 (#140)` байт от буфера 0: `#C000` → `#C140`. Этот offset — в
**знакоместах внутри дескриптора**, а не CPU-адрес; не подставляйте его как `#C040`.

«Скопировать режим с одного экрана на другой» = вызвать `SetVMod` дважды (`B=1`, затем
`B=0`); DSS подставит правильные дескрипторы для каждого экрана.

### Смешанные режимы (графика + текст в разных областях)

На уровне железа **каждое знакоместо 8×8 имеет свой 4-байтный дескриптор** (`MODE0…MODE3`,
см. [раздел про config-строки](#карта-1024-байт-одной-строки)). Байт `MODE0` задаёт класс
(текст/графика), палитру/набор символов и геометрию — поэтому железо умеет показывать
графику в одной части экрана и текст в другой.

⚠️ **Штатного DSS/BIOS API для пер-региональных смешанных режимов нет.** `SetVMod` ставит
один режим на всё окно. Смешанные режимы достигаются **прямой записью `MODE0`-дескрипторов
в config-строки** (продвинутый путь, требует понимания формата и проверки на железе) либо
собственным ACEX-битстримом (как в некоторых играх). Пишите только в декодируемую область
(`$300…$39F`); `$3A0…$3DF` стандартной прошивкой не декодируется.

## Бордюр

### В ZX-режиме — через порт #FE (нижние 3 бита)

```asm
        ld      a, 1            ; синий
        out     (#FE), a        ; ZX-бордюр
```

### В нативных режимах — через #C2/#CA (биты [2:0] BORDER)

В документации FPGA регистр `BORDER[7..0]` содержит биты [2:0] цвета бордюра.

## Double Buffering

Техника, позволяющая рисовать следующий кадр во **втором буфере**, пока первый отображается. Переключение мгновенное (на следующем VSync).

### Механизм

- Оба буфера доступны CPU через одно окно `#50` + `PORT_Y`; различаются **базой**:
  буфер 0 — `#C000`, буфер 1 — `#C140` (разница 320 байт). Отдельных страниц `#55`–`#59`
  для рисования во «второй экран» нет (см. [5.7](07_double_buffer.md)).
- Порт `#C9` (RGMOD) бит 0 определяет отображаемый буфер:
  - `RGMOD bit 0 = 0` → виден буфер 0 (`#C000`), рисуем в буфер 1 (`#C140`)
  - `RGMOD bit 0 = 1` → виден буфер 1 (`#C140`), рисуем в буфер 0 (`#C000`)

### Переключение

```asm
; Flip (переключить активный буфер)
        in      a, (#C9)        ; RGMOD
        xor     1
        out     (#C9), a
```

Пример из flappybird:
```asm
ChangeVideoPage:
        in      a, (RGMOD)
        xor     1
        out     (RGMOD), a
        ret
```

## Аппаратный акселератор (blitter)

Это специальный блок в ACEX, который **перехватывает инструкции `LD r,r`** с одинаковыми регистрами на M1-цикле и выполняет блочные операции с VRAM быстрее, чем CPU.

| Инструкция | Действие | Параметры |
|-----------|---------|----------|
| `LD B,B` | Выключить акселератор | — |
| `LD D,D` | Установить размер блока | `A` = размер |
| `LD C,C` | Заполнить блок | `A` = значение, `HL` = адрес VRAM |
| `LD E,E` | Вертикальное заполнение | `A` = значение, `HL` = адрес |
| `LD H,H` | Двухбайтная функция | — |
| `LD L,L` | Копировать строку | `HL` = src, `DE` = dst, `A` = размер |
| `LD A,A` | Копировать вертикально | аналогично |

Акселератор работает на частоте **42 МГц** и не зависит от turbo-режима Z80.

> Подробнее см. раздел [5.6 Акселератор](06_accelerator.md).

## Важно: PORT_Y и «мусор» на экране

**Порт `#89` (`PORT_Y`)** — это не обычный регистр, а индекс строки для доступа к VRAM. Аппаратура использует его значение как Y-координату, по которой идёт запись/чтение в видеопамять. Следствия:

1. Если программа записывает в VRAM (`LD (HL), A` при WIN* → VRAM-страница) и `PORT_Y` указывает на **видимую строку** (0–191/255), следующая инструкция, которую выполняет Z80 — особенно если адрес кода или данных попадает в ту же VRAM — может **исказить пиксели** этой строки. На экране это проявляется как «мусор» в случайных местах.
2. Даже обычные чтения/записи переменных могут «просвечивать» в VRAM, если забыть снять маппинг страницы.

### Правило №1: после работы с VRAM задвигать PORT_Y за пределы видимой области

SDK (см. `zx-sprinter-sdk/sdk/src/sprinter/lib_startup.asm`, `_clear_screen`, `_swap_screen`) всегда завершает работу с PORT_Y командой:

```asm
        ld      a, #C0                  ; 192 — за нижним краем
        out     (PORT_Y), a
```

Это **обязательный** приём: загнать Y-координату в область 192–255, где любой доступ к VRAM не отразится на видимом изображении. Без этого после каждого `RET`/прерывания на экране появляется мусор.

```asm
; Правильный паттерн работы с VRAM
        di
        ld      a, <row>
        out     (PORT_Y), a             ; установить строку
        ld      d, d                    ; акселератор
        ld      a, <size>
        ld      l, l                    ; копирование
        ei

        ; ОБЯЗАТЕЛЬНО: увести PORT_Y в невидимую зону
        ld      a, #C0
        out     (PORT_Y), a
```

### Правило №2: не держать код и стек в тех же страницах, что активная VRAM

Если программа подключает VRAM-страницу (`#50`…) в одно из окон, убедитесь что:
- Код программы (`WIN2`, `#8100`) не пересекается с этой же страницей
- Стек (`#BFFF`) не оказывается в VRAM-странице
- Обработчики прерываний находятся в не-VRAM области

Если Z80 начнёт выполнять инструкцию из страницы, на которую сейчас смотрит видеоконтроллер, или запишет туда значение со стека — на экране появится мусор.

### Правило №3: канонический паттерн очистки экрана

Заливаем 192 строки активного экрана через акселератор. Счётчик строки держим в регистре `E` — **никогда не пробуй читать `PORT_Y` через `IN`**: порт `#89` write-only, и `IN A,(#89)` возвращает регистр CBL (COVOX-Blaster), а не текущий Y (подтверждено MAME, `mame/src/mame/sinclair/sprinter.cpp`).

```asm
; ClearScreen — очищает 192 строки активного экрана цветом A.
; Вход: A = байт-заливка (один цвет на пиксель).
ClearScreen:
        push    af
        ld      a, VPAGE_TILES
        out     (PAGE1), a              ; WIN1 = VRAM #50

        ld      hl, #4160               ; начало пикселей строки в WIN1
        ld      a, (_screenActive)
        and     1
        jr      nz, .m1
        ld      hl, #4020               ; второй экран — другой X-сдвиг
.m1:
        ld      e, 32                   ; счётчик строки (Y), начинаем с 32
        ld      a, e
        out     (PORT_Y), a             ; PORT_Y = стартовая строка

        di
        ld      d, d : ld a, 0 : ld b, b ; настройка акселератора (LD D,D)
        pop     af                      ; A = цвет заливки
        ld      b, 192                  ; число строк
.lp1:   di
        ld      c, c                    ; LD C,C — заполнить строку через accel
        ld      (hl), a
        ld      b, b                    ; LD B,B — выключить accel
        ei

        inc     e                       ; следующая строка
        push    af
        ld      a, e
        out     (PORT_Y), a             ; PORT_Y = E
        pop     af
        djnz    .lp1

        ld      a, #C0
        out     (PORT_Y), a             ; PORT_Y в безопасную зону
        MRestoreMemMap12
        ret
```

Ключевые моменты:

1. Стартовый Y кладём в `E` и одновременно в `PORT_Y` — дальше работаем только с `E`.
2. После каждой строки `inc e` / `out (PORT_Y), e` — без обратного чтения.
3. В конце — `out (#89), #C0` (безопасная зона `$C0..$FF`), чтобы любое последующее «случайное» обращение к VRAM не плодило мусор.
4. Внутренний `DI/EI` вокруг трёх accel-байт нужен, чтобы прерывание не вклинилось между `LD D,D` и `LD B,B` (см. [5.6 Акселератор](06_accelerator.md)).

## Интервал VSync

Кадровые прерывания генерируются в конце обратного хода (аналогично ZX Spectrum) с частотой 50 Гц (PAL) или 60 Гц (NTSC). Программа может использовать прерывание для:
- Синхронизации отрисовки (double buffer flip)
- Обновления анимации
- Чтения ввода
- Воспроизведения звука (COVOX DMA)

Подробности — в разделе [9.1 Прерывания](../09_advanced/01_interrupts.md).

---

## Ключевые моменты

> - VRAM = 512 КБ, 4 параллельных банка по 8 бит.
> - Режимы: ZX (256×192), 320×256 8bpp, 640×256 4bpp.
> - VRAM страницы: `#50`–`#5F` через стандартный банкинг.
> - Порты: `#C3` (режим), `#89` (палитра), `#C9` (RGMOD, double buffer), `#C2/#CA` (бордюр).
> - Акселератор работает на 42 МГц через перехват `LD r,r`.
> - Установка режима через `Dss.SetVMod #50` проще, чем прямая запись в порты.
