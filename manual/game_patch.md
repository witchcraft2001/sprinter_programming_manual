# Game Config (Thunder in the Deep) — анализ MAME и план портирования на ACEX K50

> Этот документ — research-заметка, не часть основного руководства. Описывает различия между **стандартной** ACEX-конфигурацией Sprinter и **Game Config** (битстрим, под который заточена игра *Thunder in the Deep*), и набрасывает план дополнения исходников `acex/K50/` так, чтобы получить эквивалентный Game-битстрим, собираемый под EP1K50.
>
> Источники анализа:
> * `mame/src/mame/sinclair/sprinter.cpp` (текущая ветка) — функции `screen_update_graph`, `screen_update_game`, `as_mode`, `lookback_scroll`, `vram_w`, `m_conf` / `m_bitstream_hash`.
> * `sprinter_ai_doc/sp-altera-src-2025-11-30/altera/acex/K50/VIDEO2.TDF` — единственная публично доступная (standard) видеоконфигурация.

---

## 1. Контекст

* Текущий публичный комплект ACEX-исходников (`sp-altera-src-2025-11-30`) содержит **только стандартную конфигурацию**. K50 и K30 различаются только целевым FPGA (EP1K50/EP1K30 — разные количества LE), TDF-файлы у них идентичны.
* В природе существует **отдельный битстрим Game Config** под EP1K30, под него собрана игра *Thunder in the Deep*. Его исходники в открытый доступ не выкладывались.
* В MAME конфигурация распознаётся по хэшу битстрима:

  ```cpp
  // sprinter.cpp:1226
  m_conf &= m_bitstream_hash == 0x3861cfa4;  // Game Config
  ```

  Когда `m_conf == 1`, MAME переключает рендер с `screen_update_graph` на `screen_update_game`.

* На реальном железе EP1K50 битстрим, скомпилированный под EP1K30, не загрузится — формат `.sof` привязан к конкретному устройству (количество LE, routing, тайминги). Поэтому игра не работает на K50-плате, даже если положить туда «правильный» битстрим.

**Цель данного документа:** описать, что именно делает Game Config (поведенчески, по MAME), и предложить структуру изменений `acex/K50/VIDEO2.TDF`, при которых из K50-исходников можно собрать функционально эквивалентный Game-битстрим под EP1K50.

## 2. Сводка различий

| Аспект | Standard (`screen_update_graph`) | Game Config (`screen_update_game`) |
|---|---|---|
| Регистр `MODE3` | не подключён | задействован, источник scroll-байтов |
| Алгоритм рендера | потайловый (8×16-пиксельные клетки) | построчный (per-scanline) |
| Источник X/Y тайла | `MODE1[7..3]<<3` / `MODE0[3..0]<<6` (через `RSVA`) | `x = (MODE0[1..0]<<8) | MODE1`, `y = MODE2` (10-битный X) |
| Scroll | нет | есть, 8 бит на макроячейку (4+4) |
| Carry-over scroll | — | да, между соседними ячейками вправо/вниз |
| Условие потребления scroll | — | `MODE0[2] == 1` на границе макроячейки 16 пикс |
| Бордерная подмена пикселя | `MODE0[7..4] == 15` | `MODE0[7..5] == 7` (3 бита, не 4) |

## 3. Регистр `MODE3` (scroll-байт)

В стандартной K50-конфигурации (`VIDEO2.TDF:189-190`):

```ahdl
MODE1[7..0]   : DFFE;
MODE2[7..0]   : DFFE;
-- MODE3[7..0] : DFF;    -- закомментирован
```

Все три активных регистра (`MODE0/1/2`) защёлкиваются от шин `VDM3/VDM2/VDM1` (3 из 4 параллельных банков VRAM) в момент `LWR_MODE`. Четвёртый банк `VDM0` в этой фазе доступен, но в standard он отдан под пиксельный поток (`D_PIC0_[] = D_PICX_[]`).

В Game Config `MODE3` подключён к `VDM0` (в фазу `VCM[1..0] == 1` — фазу чтения mode-дескрипторов) и интерпретируется как:

```
MODE3:  bits [7..4] = y_scroll (0..15)
        bits [3..0] = x_scroll (0..15, в единицах пары пикселей)
```

То есть полный 4-байтный дескриптор для одной макроячейки:

```
+0  MODE0  control flags
+1  MODE1  x_low (8 бит из 10-битного X тайла)
+2  MODE2  y     (8-битный Y тайла)
+3  MODE3  scroll = { y[7..4], x[3..0] }
```

## 4. Адресация тайла в Game Config

В стандартном режиме адресация тайла идёт через регистр `SVA[]`, собираемый в `VIDEO2.TDF:495-527` по сложной таблице с участием `RGMOD`, `RSVA`, `M_CT`/`M_CTV` (счётчики растрового положения). 320×256, 8bpp, экраны A/B и т.д.

В Game Config адресация **прямая, линейная**:

```cpp
// screen_update_game, MAME sprinter.cpp:553-560
x = ((BIT(mode[0], 0, 2) << 8) | mode[1]);   // 10-битный X = MODE0[1..0]:MODE1
y = mode[2];                                  // 8-битный Y
...
*pix++ = pal + m_vram[(y + (b8 & 7)) * 1024 + x + ((a16 & 15) >> 1)];
```

Расшифровка:

* `m_vram[ROW * 1024 + COL]` — это «честный» байт VRAM. ROW = индекс 1024-байтной строки VRAM-страницы `#50`, COL = смещение 0..1023.
* `ROW = y + (b8 & 7)` — старт-Y из MODE2 плюс смещение внутри 8-пиксельной полосы (0..7). То есть тайл занимает 8 последовательных VRAM-строк, начиная с `y`.
* `COL = x + ((a16 & 15) >> 1)` — старт-X из {MODE0[1:0]:MODE1} плюс 0..7 внутри макроячейки. Деление a16 на 2 объясняет, почему x_scroll в дескрипторе — «в парах пикселей»: один байт VRAM = 2 пикселя экрана (видимо game-режим использует упакованный формат `4bpp` или packed 2px/byte, в отличие от standard `1byte=1pixel`).
* `b8` — смещение в столбце по вертикали с учётом активного scroll: `b8 = vpos + scroll.y` (фрагмент строки 547 MAME).
* `a16` — смещение по горизонтали с учётом scroll: `a16 = hpos + (scroll.x << 1)` (сдвиг на 1 = пересчёт пар пикселей в пиксели).
* Палитровая группа: `pal = MODE0[7..6] << 8` — 4 палитровых группы по 256 цветов; итоговый пиксель `pal + индекс` адресует один из `256 × 4` слотов.

Следствие: тайлы в Game Config — это произвольные 8-пиксельных полос в VRAM, на которые ссылается дескриптор. Графика тайла занимает `8 строк × N байт` (где N зависит от ширины тайла, реально читаются 8 байт на 16-пиксельную клетку).

## 5. Scroll, lookback и carry-over

### Семантика scroll по MAME

```cpp
// screen_update_game, MAME sprinter.cpp:539-567
for (u16 hpos = ...; ...) {
    u16 a16 = ... + (scroll.first << 1) ...;       // X со scroll-ом
    if (mode && BIT(mode[0], 2) && ((a16 - sc_x<<1) & 15) == 0) {
        scroll = {mode[3] & 0x0f, mode[3] >> 4};   // защёлкиваем НА ВХОДЕ в клетку
        a16 = ... + (scroll.first << 1) ...;
    }
    const u16 b8 = ... + scroll.second ...;        // Y со scroll-ом

    if (mode == nullptr) {                         // загружаем дескриптор клетки
        mode = as_mode(a16 >> 4, b8 >> 3);
        pal = ...;
        x = ...;
        y = ...;
    }
    ...
    if ((a16 & 15) == 15) {                        // на ВЫХОДЕ из клетки
        if (BIT(mode[0], 2))
            scroll = {mode[3] & 0x0f, mode[3] >> 4};  // обновляем для следующей
        mode = nullptr;
    }
}
```

Ключевое:

* **`MODE0[2]` — флаг «эта клетка задаёт scroll»**. Без флага клетка наследует scroll от соседа.
* Scroll защёлкивается **дважды** в MAME: на входе в клетку (если флаг стоит) и на выходе. Это упрощает программную модель: эффективный scroll внутри клетки определяется самим дескриптором клетки, а следующая клетка стартует с уже обновлённым scroll-ом.
* Между клетками без флага scroll **тянется** (carry-over) от последней «активной».

### `lookback_scroll` — программная аппроксимация наследования

```cpp
// MAME sprinter.cpp:580-593
std::pair<u8, u8> sprinter_state::lookback_scroll(u8 a, u8 b) {
    for (auto v = b; b; b--, a = 55)         // идём вверх по строкам
        for (auto h = a; a; a--) {           // в каждой строке — влево
            const u8* mode = as_mode(h, v);
            if (BIT(mode[0], 2) && (h != a) && (v != b))
                return { mode[3] & 0x0f, mode[3] >> 4 };
        }
    return {0, 0};
}
```

Этот lookback **в реальном железе невозможен** (произвольный обход вверх/влево по всей VRAM на каждой scanline). В оригинальном Game-битстриме почти наверняка реализован более простой механизм — **carry-over на границах строк**:

* scroll сохраняется в `DFF` и переносится с конца предыдущей scanline на начало следующей,
* в начале кадра (V-blank → активная зона) scroll сбрасывается в 0,
* программа добивается «глобального» scroll-эффекта, помечая `MODE0[2]` в **первой клетке** каждой строки (или каждой группы строк).

MAME эмулирует это software-walk-ом для надёжности. Для FPGA-реализации достаточно одного 8-битного scroll-аккумулятора с тремя точками клокирования: (1) на границе клетки при `MODE0[2]`, (2) сброс в начале кадра, (3) опциональная защёлка с конца строки на начало следующей.

## 6. Программирование scroll-дескрипторов (для прикладного программиста)

### Карта дескриптора

Координаты макроячейки: `col = 0..39` (горизонтальная позиция в 16-пиксельных шагах), `row = 0..31` (вертикальная позиция в 8-пиксельных шагах).

Адрес дескриптора в VRAM-странице `#50` (по `as_mode`):

```
VRAM row    = 1 + 2*col + 0x80 * (RGMOD bit 0)
VRAM offset = 0x300 + 4*row
4 байта     = { MODE0, MODE1, MODE2, MODE3 }
```

Чтобы записать дескриптор макроячейки `(col, row)`:

```asm
        ld      a, #1 + 2*col   ; например, col=5 → A = #0B
        out     (#89), a        ; PORT_Y = строка VRAM с дескрипторами столбца
        ; теперь VRAM #50 в любом окне показывает строку дескрипторов столбца col

        ; маппинг VRAM в WIN3 (как для палитры)
        ld      a, #50
        out     (#E2), a

        ld      hl, #C300 + 4*row    ; адрес дескриптора в WIN3
        ld      (hl), mode0
        inc     hl
        ld      (hl), mode1
        inc     hl
        ld      (hl), mode2
        inc     hl
        ld      (hl), mode3          ; scroll = {y[7..4], x[3..0]}
```

### Биты `MODE0`

| Бит    | Значение                                          |
|--------|--------------------------------------------------|
| [1..0] | x_high — старшие 2 бита 10-битного X-адреса тайла |
| [2]    | scroll-update flag (1 = эта клетка задаёт новый scroll) |
| [4..3] | (резерв / зависит от режима 320/640)              |
| [5..3]==7 | специальный border-пиксель: `pen = $400 + цвет из FE` |
| [7..6] | палитровая группа (4 группы по 256 цветов)        |

### Биты `MODE3` (scroll)

```
MODE3 = (y_scroll << 4) | (x_scroll & 0x0F)
```

* `x_scroll`: 0..15, единица = 2 пикселя экрана (т.е. реальный сдвиг = `x_scroll * 2`).
* `y_scroll`: 0..15, единица = 1 строка.

### Программные сценарии

**Статический горизонтальный скролл всей картинки.** Достаточно одной активной клетки в начале:

```asm
; для каждой строки макроячеек row = 0..31:
;   дескриптор (col=0, row): MODE0 |= 0x04 (scroll-update), MODE3 = scroll_x
;   все остальные клетки наследуют через carry-over
```

**Параллакс-слои.** Разные строки макроячеек получают разный scroll:

```
row 0..7   → mode3.x_scroll = far_layer_scroll        (медленный, дальний план)
row 8..23  → mode3.x_scroll = mid_layer_scroll        (средний)
row 24..31 → mode3.x_scroll = near_layer_scroll       (быстрый, передний план)
```

В первом дескрипторе каждой группы строк взвести `MODE0[2]`, в остальных — оставить 0.

**Локальные «качающиеся» области.** В клетке (col=10, row=5) поставить `MODE0[2]=1` и менять `MODE3.x_scroll` каждый кадр по синусоиде → область 16×8 пикселей колеблется относительно фона. Соседи через carry-over подцепят то же значение, поэтому для изолированного эффекта в следующей клетке (col=11, row=5) поставить `MODE0[2]=1, MODE3=0`, явно «отменяя» scroll.

**Плавный сдвиг с под-пиксельной точностью.** Аппаратный x_scroll работает с шагом 2 пикселя. Для шага 1 пиксель нужно дополнительно сдвигать содержимое тайла (`MODE1`), либо использовать половинные тайлы — это уже забота приложения.

### Ограничения

* Scroll действует **в пределах макроячейки 16×8 пикселей**, дальнейший сдвиг — через изменение базового X/Y тайла в `MODE1`/`MODE2`.
* Carry-over в пределах строки работает влево→вправо; для вертикального наследования нужно явно ставить `MODE0[2]` в первой клетке каждой следующей строки.
* `MODE0[2]` использует тот же байт, что и палитровая группа и x_high — менять scroll-флаг нужно осторожно, не затирая остальные поля.

## 7. План доработки `acex/K50/VIDEO2.TDF`

Цель: получить **второй** `.sof`-файл (Game-битстрим под EP1K50), который MAME должен распознать как Game Config. Стандартный битстрим остаётся как есть.

### 7.1. Стратегия — отдельная сборка, не runtime-переключение

В ACEX1K мало логических элементов (EP1K50 = 2880 LE), и две полные ветки рендера одновременно вряд ли влезут. Поэтому:

1. Параметризовать `VIDEO2.TDF` через `PARAMETERS (CONF = "STANDARD")`.
2. Все Game-специфичные блоки обернуть в `IF CONF == "GAME" GENERATE … END GENERATE;`.
3. На уровне `SP2_ACEX.TDF` поднять параметр в проектный.
4. В Quartus II 13.0sp1 создать вторую цель сборки `SP2_ACEX_GAME` с `CONF="GAME"` и привязать к EP1K50.

После сборки итоговый `.sof` будет иметь другой хэш — MAME `sprinter.cpp:1226` придётся доучить (см. п. 7.5).

### 7.2. Изменения в `VIDEO2.TDF`

**(a) Регистр MODE3.**

```ahdl
VARIABLE
    ...
    MODE3[7..0]   : DFFE;     -- раскомментировать
```

```ahdl
IF CONF == "GAME" GENERATE
    MODE3[].ena = VCC;
    MODE3[].clk = LWR_MODE;
    MODE3[].d   = VDM0[];     -- 4-й банк, в фазу чтения дескрипторов
END GENERATE;
```

Внимание: в стандартном режиме `D_PIC0_[] = VDM0[]` — пиксельный поток. В Game-режиме `VDM0` в фазе `VCM == 1` (фаза дескрипторов) должен подменяться на MODE3, а в фазе `VCM == 0` (фаза пикселей) — оставаться пиксельным потоком. Реализуется через мультиплексор по `VCM[1..0]`.

**(b) Scroll-аккумулятор.**

```ahdl
IF CONF == "GAME" GENERATE
    SCRX[3..0] : DFFE;
    SCRY[3..0] : DFFE;

    -- захват по границе макроячейки при MODE0[2]==1
    CAPTURE_SCROLL = LCELL(MODE0[2] AND CELL_BOUND);
    SCRX[].clk = CLK42;
    SCRX[].ena = CAPTURE_SCROLL;
    SCRX[].d   = MODE3[3..0];
    SCRY[].clk = CLK42;
    SCRY[].ena = CAPTURE_SCROLL;
    SCRY[].d   = MODE3[7..4];

    -- сброс scroll в начале кадра (V-blank → active)
    SCRX[].clrn = !FRAME_START;
    SCRY[].clrn = !FRAME_START;
END GENERATE;
```

`CELL_BOUND` — комбинация счётчика горизонтальной позиции на нуле младших 4 битов; `FRAME_START` — V-blank-выход.

**(c) Альтернативная адресация пикселя тайла.**

Standard собирает `SVA[]` через `CASE (!VCM2, MODE0[4])` (строки 505–528) — это адрес для тайла/символа с разрешением 320/640 и режимом graph/text. В Game-режиме нужен другой `SVA`:

```ahdl
IF CONF == "GAME" GENERATE
    -- эффективный X тайла: 10 бит, со scroll-ом
    -- x_tile = (MODE0[1..0], MODE1[7..0]) + (SCRX[3..0] << 1)
    GX[9..0] = (MODE0[1..0], MODE1[7..0]) + (SCRX[3..0], GND);

    -- эффективный Y: 8 бит со scroll-ом + 3 бита внутри полосы
    GY[10..0] = (MODE2[7..0] + SCRY[3..0], CTV[2..0]);

    -- финальный адрес в VRAM-странице 50: Y * 1024 + X / 2
    SVA[] = ( GY[10..0], GX[9..1] );    -- битовая ширина SVA[18..0]
END GENERATE;
```

(Это набросок — точная разрядность и порядок битов зависят от того, как `SVA[]` декодируется дальше в `V_CST/V_WE`-логике на строках 432–490.)

**(d) Бордерная подмена.**

Standard: `BORD = DFF((MODE0[7..4] == 15), LWR_COL, , );` (строка 414).
Game: `BORD = DFF((MODE0[7..5] == 7), LWR_COL, , );` — сравнение 3 бит, не 4.

Это можно переписать через мультиплексор по `CONF` без `GENERATE`-блока.

**(e) Carry-over scroll по концу строки (опционально).**

```ahdl
IF CONF == "GAME" GENERATE
    -- защёлкиваем scroll на конце строки в "теневые" регистры,
    -- восстанавливаем в начале следующей строки
    SCRX_HOLD[3..0].d = SCRX[3..0];
    SCRX_HOLD[3..0].clk = LINE_END;
    SCRY_HOLD[3..0].d = SCRY[3..0];
    SCRY_HOLD[3..0].clk = LINE_END;

    -- в начале строки, если первая клетка не помечена MODE0[2],
    -- scroll возвращается из *_HOLD
    ...
END GENERATE;
```

Это эквивалент упрощённого lookback (только carry-over с предыдущей scanline). Если поведение в MAME критично воспроизвести точно — пробовать без этой части сначала, чтобы оценить минимально достаточное.

### 7.3. Изменения в `SP2_ACEX.TDF`

```ahdl
PARAMETERS (CONF = "STANDARD");
...
video2_inst : video2 WITH (
    MODE = "SPRINTER",
    MOUSE = "NO",
    CONF = CONF             -- проброс параметра
) ...
```

Создать два Quartus-revisions: `SP2_ACEX_STD` (default) и `SP2_ACEX_GAME` (с `CONF="GAME"` в верхних параметрах).

### 7.4. Бюджет и тайминги

* EP1K50 = 2880 LE. Текущая `VIDEO2.TDF` плюс прочие модули (`ACCELER`, `AY`, `DCP`, `KBD`, `MOUSE`) укладываются в EP1K30 = 1728 LE. Запас под Game-логику ≈ 1100 LE — должен хватить с большим запасом, но реальная цифра после fitting проверяется только по отчёту Quartus.
* Критическая частота — `CLK42` (42 МГц). Добавление scroll-сумматора и MUX в `SVA` удлинит критический путь; нужно валидировать через TimeQuest. При просадке slack — выносить сумматор в дополнительную регистровую ступень (`SCRX_REG → SUM_REG → SVA`).

### 7.5. Изменения в MAME

После сборки Game-битстрима под EP1K50 у него будет **свой хэш** — `0x3861cfa4` (текущая константа в `sprinter.cpp:1226`) не подойдёт. Варианты:

1. Добавить второй хэш в условие:
   ```cpp
   m_conf &= (m_bitstream_hash == 0x3861cfa4)
          || (m_bitstream_hash == 0xXXXXXXXX);  // K50 Game build
   ```
2. Или вообще убрать привязку к хэшу и завести явный пользовательский ключ конфигурации в MAME slot-опциях.

Лучше первое — даёт обратную совместимость с существующим K30-битстримом для тех, у кого K30-плата.

### 7.6. Этапность работы

1. **MODE3 read-path.** Раскомментировать регистр, подключить к VDM0 через MUX по фазе. Проверить дампом VRAM в MAME, что значения дескрипторов читаются.
2. **Статический scroll.** Реализовать только захват MODE3 в SCRX/SCRY на `MODE0[2]`. На простой тест-картинке (одна горизонтально-полосатая текстура с дескриптором `MODE0=0x04, MODE3=0x03`) убедиться, что фон сдвигается на 6 пикселей.
3. **Carry-over.** Добавить логику наследования между соседними клетками без `MODE0[2]`.
4. **Бордер-подмена.** Переписать `BORD` по новому условию.
5. **Verification против MAME.** Запустить тестовую программу в MAME с `m_conf=1` (форсированно, без проверки хэша) и сравнить кадровые рендеры. Идентичность по пикселям не обязательна (lookback в MAME — software, в железе carry-over) — главное, чтобы Thunder in the Deep отображалась корректно.
6. **Финальная сборка.** Quartus → `.sof` → загрузка в плату K50 → визуальный тест с TitD.

## 8. Что осталось неясным

* **Точный формат хранения тайл-графики в game-режиме.** MAME читает по адресу `(y + (b8 & 7)) * 1024 + x + ((a16 & 15) >> 1)`, явно по 1 байту на 2 пикселя — это 4bpp packed. Но как именно ниббл выбирается из байта (`a16 & 1` определяет старший/младший?), в MAME не показано — нужно смотреть код TitD или экспериментировать.
* **Точная семантика `(h != a) && (v != b)`** в `lookback_scroll` — выглядит как «не возвращай scroll самой стартовой клетки», но эта же логика мешает наследовать scroll из (a-1, b-1) и подобных. Возможно, это эвристика MAME, а не точное копирование железа.
* **Источник `FRAME_START` и `LINE_END`** в существующей `VIDEO2.TDF`. Сигналы есть (`CTV`/`CTH` счётчики), но нужно подобрать точные комбинации под фазу `LWR_MODE`.
* **Битовая ширина `SVA[]` в Game-варианте.** Standard работает с 18 битами, и Game-формула даёт похожий объём, но точный битовый порядок (`VLA` сборка в `CASE VCM[1..0]`) нужно сверять с `V_CST`/`V_WE`-обвязкой.
* **`MODE0[3]`, `MODE0[4]`** — в standard это режимные биты (graph/text, 320/640). В game-режиме их роль из MAME не извлекается напрямую — возможно, переопределены, возможно, используются как обычно.

Все эти неизвестные разрешаются либо чтением TitD-кода (если найдётся), либо итеративным экспериментом «правка TDF → пересборка → визуал в MAME».

## 9. Резюме

* Game Config — **отдельный битстрим** под EP1K30. Чтобы он заработал на EP1K50, нужно пересобирать из исходников, которых публично нет.
* Behavioral-эталон есть в MAME — `screen_update_game` + `lookback_scroll`. Этого достаточно для воспроизведения большинства видимых эффектов.
* Минимальный набор изменений ACEX K50: подключить `MODE3` от `VDM0` в фазе дескрипторов, добавить 8-битный scroll-аккумулятор (захват по `MODE0[2]` на границах макроячеек), переключить адресацию пикселя на game-формулу, пофиксить условие бордера на 3 бита.
* Параметризация через `PARAMETERS (CONF)` + `GENERATE` позволяет держать обе ветки в одном дереве TDF и собирать два независимых битстрима.
* MAME-сторону придётся подучить распознавать новый хэш битстрима.
* Ориентировочная трудоёмкость — 1–2 недели опытного AHDL-разработчика, основное время уходит на отладку scroll-семантики и тайминги под 42 МГц.
