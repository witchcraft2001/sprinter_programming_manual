# 5.7 Двойная буферизация (Double Buffering)

> **Навигация:** [← 5.6 Акселератор](06_accelerator.md) | [Оглавление](../README.md) | [5.8 Текстовый режим →](08_text_mode.md)

---

## Зачем нужна двойная буферизация

Без двойной буферизации программа рисует непосредственно в активный видеобуфер. Если обновление кадра занимает дольше одного интервала VSync, пользователь видит **tearing** — горизонтальные разрывы, где часть экрана уже обновлена, а часть ещё нет.

**Double buffering** решает проблему: программа рисует в **неактивный** (невидимый) буфер, затем в момент VSync переключает его на **активный**. Переключение мгновенное, tearing исчезает.

---

## Организация VRAM в Sprinter

VRAM 512 КБ хранит **два экрана 320×256** одновременно. Физически каждый экран занимает
~80 КБ, но **процессор обращается к обоим буферам не как к отдельным линейным страницам**,
а через одно окно `#50` с выбором строки через `PORT_Y` (см. ниже). Не пытайтесь рисовать
во «второй экран», мапя в окно страницу `#55` — это неверный путь для double-buffer.

---

## Как буфер виден процессору (CPU-view) — ОБЯЗАТЕЛЬНО к прочтению

Это центральная деталь, без которой прямой вывод не заработает. Видеопамять режима
320×256×8 **не отображается в адреса Z80 линейно**. CPU «видит» её через **скользящее
окно одной строки растра**:

- В **WIN3** (`#C000–#FFFF`, порт `#E2`) маппится **VRAM-страница `#50`**.
- Порт **`PORT_Y` (`#89`, только запись)** выбирает текущую **строку растра 0..255**.
- Для выбранной строки оба буфера лежат рядом (1 байт = 1 пиксель, 8 bpp):

| CPU-адрес | Что это |
|-----------|---------|
| `#C000 + x` | пиксель `(x, PORT_Y)` **буфера 0**, `x = 0..319` |
| `#C140 + x` | пиксель `(x, PORT_Y)` **буфера 1**, `x = 0..319` |

```asm
; Записать пиксель (x, y) цветом COLOR в буфер 0.
        ld      a, #50
        out     (#E2), a            ; WIN3 = VRAM-страница #50
        ld      a, y
        out     (#89), a            ; PORT_Y = строка растра
        ld      hl, #C000
        ld      b, #0
        ld      c, x                ; (x как 16-бит, см. «Подводные камни»)
        add     hl, bc              ; HL = #C000 + x
        ld      (hl), COLOR
        ld      a, #C0
        out     (#89), a            ; «припарковать» PORT_Y на невидимую строку
```

**Ключевые факты (подтверждены рабочим кодом и дескриптором экрана из DSS):**

1. `#C000` и `#C140` — это **базы двух буферов в ОДНОЙ строке** страницы `#50`. Это **не**
   два разных экрана и **не** страница `#55`. Оба буфера доступны одновременно в окне `#50`.
2. Разница между базами буферов = **320 байт (`#140`)**, а **не** `#40`. (320 = 40
   знакомест × 8 px — это «VRAM X offset» страницы 1 в дескрипторе экрана, см.
   [5.1](01_video_overview.md) и [5.3](03_mode1_320.md).)
3. Строка — **320 байт**. Переход на другую строку — это **смена `PORT_Y`**, а не
   прибавление к адресу: `HL` остаётся базой строки.
4. `x` — **16-битное** байтовое смещение (доходит до 319). 8-битная арифметика смещения
   даёт видимый заворот картинки — см. раздел «Подводные камни» в [5.3](03_mode1_320.md).
5. Числа вида `8/48`, встречающиеся как «X offset» в дескрипторе/BIOS, — это смещения в
   **знакоместах внутри дескриптора**, а **не** CPU-базы пиксельного буфера. Не
   подставляйте их как `#C040/#C180`.

## Инициализация: режим на обоих экранах

Для одного экрана достаточно одного вызова `SetVMod` (см. [5.3](03_mode1_320.md#включение-режима)).
Но **двойная буферизация требует, чтобы РЕЖИМ был установлен на обоих экранах**: вызов
`SetVMod` для экрана 0 **не гарантирует**, что экран 1 настроен — у каждого экрана свой
дескриптор (см. [5.1](01_video_overview.md#дескриптор-экрана-что-именно-делает-setvmod)).
Поэтому инициализируйте оба, сначала `B=1`, затем `B=0`:

```asm
        ld      a, #81              ; 320×256×256c
        ld      b, #01              ; экран 1
        ld      c, #50              ; Dss.SetVMod
        rst     #10

        ld      a, #81
        ld      b, #00              ; экран 0 (остаётся отображаемым)
        ld      c, #50
        rst     #10
```

> Если настроить только один экран, второй буфер при первом же flip покажет чёрный/
> мусорный кадр или другой видеорежим. Порядок `B=1` затем `B=0` оставляет отображаемым
> экран 0.

## Регистр RGMOD (порт #C9)

Управляет режимом видеовывода. Биты регистра подаются напрямую в сигналы видеоконтроллера (`DIR_PORT`) из `SP2_ACEX.TDF` (и `SP2_1K30.TDF` в BIOS 2.17):

```
SVIDEO.DIR_PORT[3] = RGMOD0;   -- выбор отображаемой страницы (0 = экран A, 1 = экран B)
SVIDEO.DIR_PORT[4] = RGMOD1;   -- принудительное гашение кадра (только если SCREEN_OFF="USE")
```

| Бит | Назначение |
|-----|-----------|
| 0 | **Выбор отображаемого буфера:** 0 = виден буфер 0 (CPU-база `#C000`), 1 = виден буфер 1 (CPU-база `#C140`).|
| 1 | **Гашение видеосигнала:** 1 = сигнал BLANK принудительно установлен, кадр не выводится. В стандартной прошивке **не подключён** (`SCREEN_OFF = "NOT_USE"` по умолчанию) |
| [7:2] | Не используются |

> ⚠️ Имена `RGMOD0/RGMOD1` в исходниках FPGA — это внутренние линии `DIR_PORT[3]/[4]`, а
> **не** биты 3/4 порта `#C9`. Прикладной программе доступен только **бит 0 публичного
> порта `#C9`**; остальное управляется прошивкой (см. [5.1, «Публичные vs внутренние
> порты»](01_video_overview.md)).

В `VIDEO2.TDF` бит подключается к аппаратному сигналу BLANK:
```
BLANK = DFF(((BORD & MODE03 & MODE02) or DIR_PORT4), LWR_COL,,);
```
Когда `DIR_PORT[4] = 1`, сигнал BLANK принудительно выставлен — видеоконтроллер не выдаёт пикселей, экран гаснет. Параметр `SCREEN_OFF` в FPGA по умолчанию `"NOT_USE"`, и тогда `DIR_PORT[4] = GND` (бит 1 RGMOD просто игнорируется).

### Значения RGMOD

| Значение | Бит 1 | Бит 0 | Отображаемый буфер | Видеосигнал |
|----------|-------|-------|-------------------|-------------|
| `#00` | 0 | 0 | буфер 0 (CPU-база `#C000`) | активен |
| `#01` | 0 | 1 | буфер 1 (CPU-база `#C140`) | активен |
| `#02` | 1 | 0 | буфер 0 | погашен ¹ |
| `#03` | 1 | 1 | буфер 1 | погашен ¹ |

> ¹ Гашение работает только если прошивка FPGA собрана с параметром `SCREEN_OFF = "USE"`. В стандартной сборке BIOS этот параметр выключен — бит 1 не имеет эффекта.

Практически программу интересует только **бит 0**: переключение отображаемого буфера в цикле отрисовки.

```asm
RGMOD_SCR_A     EQU #00     ; отображать экран A (обычное начальное состояние)
RGMOD_SCR_B     EQU #01     ; отображать экран B
```

## Простая техника: flip

```asm
RGMOD           EQU #C9

; Переключить активный буфер
FlipBuffer:
        in      a, (RGMOD)
        xor     1                   ; инвертировать бит 0
        out     (RGMOD), a
        ret
```

Этот код мгновенно меняет активный экран. Если он выполняется **до VSync**, видимого tearing не будет.

---

## Правильный цикл с ожиданием VSync

Рисуем **в скрытый буфер**. Скрытый буфер — это база `#C000`, если отображается буфер 1,
и `#C140`, если отображается буфер 0 (т.е. база = «обратная» к `RGMOD & 1`). Во всех
случаях WIN3 = `#50`, а строка выбирается через `PORT_Y`.

```asm
GameLoop:
        ; 1. WIN3 = страница #50 (на всё время отрисовки в VRAM)
        ld      a, #50
        out     (#E2), a

        ; 2. Выбрать базу СКРЫТОГО буфера по RGMOD.0
        in      a, (RGMOD)
        and     1                   ; 0 = виден буфер 0, 1 = виден буфер 1
        ld      hl, #C140           ; виден 0 -> рисуем в буфер 1 (#C140)
        jr      z, .have_base
        ld      hl, #C000           ; виден 1 -> рисуем в буфер 0 (#C000)
.have_base:
        ; HL = база скрытого буфера; рисуем кадр (внутри меняем PORT_Y по строкам)
        call    DrawFrame           ; DrawFrame использует HL как базу строки + PORT_Y

        ld      a, #C0
        out     (#89), a            ; вернуть PORT_Y на невидимую строку

        ; 3. Ждать VSync (см. ниже про источник синхронизации)
        call    WaitVSync

        ; 4. Flip — переключить отображаемый буфер (RGMOD бит 0)
        in      a, (RGMOD)
        xor     1
        out     (RGMOD), a

        jr      GameLoop
```

> Внутри `DrawFrame` для каждой строки кадра выставляется `PORT_Y` (строка растра), а
> запись пикселей идёт по `HL + x` (база скрытого буфера + смещение). Сменить строку =
> сменить `PORT_Y`, а не прибавить к адресу.

## Использование SDK: _screenActive

SDK из `zx-sprinter-sdk/sdk/src/sprinter/lib_startup.asm` хранит индекс активного экрана в RAM:

```asm
_screenActive:  db  0           ; 0 или 1

; Функция swap_screen
_swap_screen:
        ; ... ожидание VSync, отрисовка спрайтов ...

        call    update_pal

        call    waitVsync       ; halt

        ld      a, (_screenActive)
        out     (RGMOD), a
        xor     1
        ld      (_screenActive), a

        ; ... обновление спрайтов для нового буфера ...
        ret
```

## Координация с отрисовкой

Частая ошибка: рисовать и в A, и в B одновременно, что приводит к "double flashing". Правильно:

1. Считать `_screenActive` → определить "скрытый" буфер.
2. Рисовать весь кадр в скрытый буфер.
3. Flip.
4. Следующий кадр — теперь рисовать в *противоположный* буфер (бывший активный).

Это значит, что **каждый кадр рисуется заново** — нельзя "накапливать" изменения, потому что между кадрами активные буферы меняются.

### Оптимизация: "дельта"-обновления

Для статичного фона можно хранить его копию в RAM и быстро копировать при каждом кадре только изменённые области:

```asm
; Каждый кадр:
; 1. В скрытый буфер скопировать фон из RAM (через акселератор)
; 2. Нарисовать подвижные объекты
; 3. Flip
```

## Синхронизация с VSync

Есть два рабочих способа дождаться начала кадра.

### Способ 1: по прерыванию (`HALT`)

```asm
; Ждать следующего VSync
WaitVSync:
        halt                        ; остановить CPU до следующего прерывания
        ret
```

`HALT` работает только при разрешённых прерываниях (`EI`). В IM1 `RST #38` вызовется
автоматически. В IM2 вектор зависит от установки.

### Способ 2: поллинг бита 5 порта `#FFFE` (без прерываний)

Подходит для кода, работающего с `DI` (загрузчики, движки на опросе). Sprinter отдаёт
признак вертикального гашения на **бите 5 порта `#FFFE`** (бит = 1, пока `Y > 256`,
т.е. в нижнем бордюре). Этот бит переключается, **только когда активен CBL** (Covox
Blaster), поэтому его сначала «заводят» записью в управляющий порт CBL. Ждём фронт
1→0 — это начало кадра:

```asm
WaitVSyncPoll:
        ld      bc, #004E           ; CBL_CTRL: завести idle-режим, чтобы #FE.5 тикал
        ld      a, #80
        out     (c), a
        ld      de, #8000           ; страховочный таймаут (не зависнуть)
.into_blank:
        ld      a, #FF
        in      a, (#FE)            ; читаем #FFFE (A=#FF старший байт адреса)
        bit     5, a
        jr      nz, .wait_frame     ; уже в нижнем гашении
        dec     de
        ld      a, d
        or      e
        jr      nz, .into_blank
        ret                         ; таймаут — выходим, не виснем
.wait_frame:
        ld      de, #8000
.loop:
        ld      a, #FF
        in      a, (#FE)
        bit     5, a
        ret     z                   ; фронт 1->0: начало кадра
        dec     de
        ld      a, d
        or      e
        jr      nz, .loop
        ret
```

> Это проверенный приём (так делает рабочий референс-код). Чистый опрос, не требует
> `EI`/`HALT`, что важно при включённом SRAM-кэше, когда таблица векторов прерываний в
> WIN0 может быть недоступна.

## Частые ошибки

### Ошибка 1: flip без ожидания VSync

```asm
; ПЛОХО
        call    DrawFrame
        call    FlipBuffer          ; может произойти в середине кадра → tearing
```

### Ошибка 2: рисование в активный буфер

```asm
; ПЛОХО
        call    DrawFrame           ; без определения активного буфера
        ; видно промежуточное состояние отрисовки
```

### Ошибка 3: не учитывать смену активного буфера между кадрами

```asm
; ПЛОХО — каждый кадр одно и то же
.game_loop:
        call    DrawSpriteInA       ; всегда в A
        call    FlipBuffer
        jr      .game_loop
; Результат: в B ничего нет → мерцание
```

### Правильно

```asm
.game_loop:
        ; Определить скрытый буфер
        in      a, (RGMOD)
        and     1
        call    SetupHiddenBufferPages  ; подключить нужные VRAM страницы

        call    DrawFrame               ; полная отрисовка

        halt                            ; VSync

        ; Flip
        in      a, (RGMOD)
        xor     1
        out     (RGMOD), a

        jr      .game_loop
```

## Double buffering и палитра

Палитр-страниц несколько (см. [5.5](05_palette.md)): страница 0 лежит в VRAM по `#C3E0`,
страница 1 — по `#C3E4`. **Отображаемая палитра следует за отображаемым буфером.** Поэтому
при flip двойного буфера цвета могут «мигнуть», если палитры страниц различаются.

Чтобы цвета были стабильны при переключении, записывайте **одинаковую палитру в обе
страницы** (`#C3E0` и `#C3E4`). Если же нужны разные палитры на двух буферах (эффекты
фейда/циклинга по кадрам) — это штатно достижимо, меняя палитру скрытой страницы перед
flip.

## Ограничения

- Double buffering работает в режимах **320×256 8bpp** и **640×256 4bpp** — оба экрана по ~80 КБ помещаются в 512 КБ VRAM.
- В ZX Spectrum режиме double buffering недоступен (только один экран ZX).
- Требует прямой доступ к VRAM через окна — не работает через BIOS функции печати текста (они пишут в текстовый слой, не в графический буфер).

---

## Ключевые моменты

> - Оба буфера доступны CPU через одно окно `WIN3=#50` + `PORT_Y`; базы `#C000` (буфер 0)
>   и `#C140` (буфер 1), разница 320 байт. **Не** мапьте страницу `#55` для рисования.
> - Отображаемый буфер выбирается **битом 0** порта `#C9` (RGMOD); рисуем в скрытый.
> - Цикл: WIN3=#50 → выбрать базу скрытого буфера по `RGMOD.0` → рисовать (строка = `PORT_Y`)
>   → ждать VSync → flip.
> - X — 16-битное смещение (0..319); 8-битная арифметика даёт заворот.
> - Каждый кадр рисуется заново (нет инкрементального накопления между буферами).
> - У каждой страницы-буфера своя палитра (`#C3E0`/`#C3E4`); для стабильных цветов пишите
>   одинаково в обе.
